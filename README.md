# Building Systems Estimator

A small, standalone backend for the Developer Technical Assessment. It simulates scanning a building twice, compares the two readings, picks equipment quantities with a documented rule, computes a repeatable price and saves the estimate.

Everything runs locally: no external services, no credentials, no network. Scans come from mock fixtures.

- **Stack:** TypeScript, Express 5, zod, SQLite (`better-sqlite3`), vitest + supertest.

## How an estimate is made

`POST /estimates` runs these steps in order:

1. **Validate** the body. Invalid input is rejected with `400`; the provider is not called and nothing is saved.
2. **Check the fixture** exists. An unknown fixture is a `400`.
3. **Stage 1, initial scan.** If it fails: `502`, nothing is saved.
4. **Stage 2, verification scan.** If it fails: the estimate is still created and a warning is recorded.
5. **Stage 3, consolidation** (plain application logic, not an AI call) and **pricing**.
6. **Save** and answer `201`.

### Selection rule

The initial scan is authoritative: its counts are always the selected ones.

- Verification disagrees: keep the initial counts, add one warning per differing equipment type (for example `Antenna count mismatch: 28 vs 26`).
- Verification failed: keep the initial counts, add the warning `Verification scan failed`, and store `scans.verification` as `null`.
- Initial scan failed: no estimate.

`status` is `completed` when there are no warnings and `completed_with_warnings` otherwise.

### Pricing (fictional, whole USD)

| Line item | Rule |
|---|---|
| Floors | $100 x floors |
| Antennas | $250 x selected antennas |
| Splitters | $80 x selected splitters |

Demo: 12 x 100 + 28 x 250 + 6 x 80 = **$8,680**.

## Quick start

Requires Node.js 20 or newer (developed on Node 22; the test suite also passes on Windows).

```bash
npm install
npm test          # runs the whole suite
npm start         # http://localhost:3000
```

Other scripts: `npm run dev` (restart on changes), `npm run typecheck`, `npm run build` (compiles to `dist/`, run with `node dist/server.js`).

### Configuration (all optional)

| Variable | Default | Meaning |
|---|---|---|
| `PORT` | `3000` | HTTP port |
| `DB_PATH` | `./data/estimates.db` | SQLite file. It and its folder are created on first start. |
| `FIXTURES_DIR` | `./fixtures` | Folder with the mock scan fixtures |

### Troubleshooting

Recent npm versions may print `install scripts blocked ... better-sqlite3`. In my runs this warning was harmless: `better-sqlite3` loaded and the tests passed. If you ever see an error about missing native bindings, allow its install script as the message suggests (`npm install-scripts approve better-sqlite3`) and reinstall.

## API

### `POST /estimates`

Request body:

```json
{ "project": "Demo Building", "floors": 12, "fixture": "demo" }
```

Response `201 Created` (with a `Location: /estimates/{id}` header):

```json
{
  "id": "est_4e652ea7-6e6a-4dff-b055-e6ab6df22be4",
  "project": "Demo Building",
  "floors": 12,
  "fixture": "demo",
  "status": "completed_with_warnings",
  "stages": { "initial": "completed", "verification": "completed", "consolidation": "completed" },
  "scans": {
    "initial": { "antennas": 28, "splitters": 6 },
    "verification": { "antennas": 26, "splitters": 6 }
  },
  "selected": { "antennas": 28, "splitters": 6 },
  "line_items": { "floors": 1200, "antennas": 7000, "splitters": 480 },
  "total": 8680,
  "warnings": ["Antenna count mismatch: 28 vs 26"],
  "created_at": "2026-10-29T03:33:11.014Z"
}
```

Validation rules (nothing is coerced, so `"12"` is not accepted as `12`):

| Field | Rule |
|---|---|
| `project` | string, not empty after trimming, at most 200 characters |
| `floors` | positive integer, at most 1000 |
| `fixture` | string, not empty after trimming, at most 100 characters; must be an available fixture |

The two upper bounds are my own addition (they keep values sane and totals exact integers). Unknown extra fields are ignored.

### `GET /estimates/{id}`

Returns `200` with the saved estimate (same shape as above), also after an application restart, or `404` if the id does not exist. Ids are generated by the application as `est_` plus a UUID.

### Errors

Every error has the same shape, so clients can always read `error.code`:

```json
{ "error": { "code": "validation_error", "message": "Request validation failed",
             "details": [ { "field": "project", "message": "must not be empty" },
                          { "field": "floors", "message": "must be a positive integer" } ] } }
```

| Situation | HTTP | `error.code` |
|---|---|---|
| Invalid field values or body is not a JSON object | 400 | `validation_error` |
| Malformed JSON | 400 | `invalid_json` |
| Fixture is not available (message lists the available ones) | 400 | `unknown_fixture` |
| Body larger than 10 KB | 413 | `payload_too_large` |
| Estimate id does not exist | 404 | `not_found` |
| Unknown route | 404 | `route_not_found` |
| The scan provider failed on the initial scan (includes `stage`) | **502** | `provider_failure` |
| Unexpected bug (details are logged, never sent to the client) | 500 | `internal_error` |

Client mistakes are always 4xx and provider failures are 5xx, so they can be told apart.

## Try it

Start the server with `npm start` first.

### Postman

Import `postman/building-systems-estimator.postman_collection.json` and run it in order (or use *Run collection*). It has 8 requests, each with tests that check the expected status and values. Request 1 saves the new id so request 2 can read it back.

### curl (macOS, Linux, Git Bash)

```bash
# Demo: 201, selected 28/6, warning about antennas, total 8680
curl -i -X POST http://localhost:3000/estimates \
  -H "Content-Type: application/json" \
  -d '{"project":"Demo Building","floors":12,"fixture":"demo"}'

# Read it back (use the id from the previous response)
curl -i http://localhost:3000/estimates/est_REPLACE_WITH_ID

# Verification fails: 201, verification null, warning "Verification scan failed", total 8680
curl -i -X POST http://localhost:3000/estimates -H "Content-Type: application/json" \
  -d '{"project":"Demo Building","floors":12,"fixture":"verification_failure"}'

# Initial scan fails: 502, nothing saved
curl -i -X POST http://localhost:3000/estimates -H "Content-Type: application/json" \
  -d '{"project":"Demo Building","floors":12,"fixture":"initial_failure"}'

# Invalid input: 400 with a message per field
curl -i -X POST http://localhost:3000/estimates -H "Content-Type: application/json" \
  -d '{"project":"","floors":0,"fixture":"demo"}'

# Unknown fixture: 400
curl -i -X POST http://localhost:3000/estimates -H "Content-Type: application/json" \
  -d '{"project":"Demo Building","floors":12,"fixture":"nope"}'
```

### Windows PowerShell

In Windows PowerShell, `curl` is an alias of `Invoke-WebRequest`, which takes different options, so the commands above do not work as written. Use `Invoke-RestMethod`:

```powershell
$body = @{ project = "Demo Building"; floors = 12; fixture = "demo" } | ConvertTo-Json
$estimate = Invoke-RestMethod -Method Post -Uri http://localhost:3000/estimates `
  -ContentType "application/json" -Body $body
$estimate                                                        # the created estimate
Invoke-RestMethod -Uri "http://localhost:3000/estimates/$($estimate.id)"   # read it back
```

`Invoke-RestMethod` throws on 4xx/5xx responses instead of printing the body, so for the error cases use Postman, or the real curl that ships with Windows (`curl.exe`) with the JSON in a file: `curl.exe -i -X POST http://localhost:3000/estimates -H "Content-Type: application/json" -d "@body.json"`.

### Check persistence across a restart

1. Create an estimate and note its `id`.
2. Stop the server (Ctrl+C) and start it again with `npm start`.
3. `GET /estimates/{id}` returns the same estimate.

## Fixtures

One JSON file per fixture in `fixtures/`; the file name (without `.json`) is the fixture id. Each stage is either `completed` with `counts`, or `failed` with an optional `error` message:

```json
{
  "description": "optional free text",
  "initial":      { "status": "completed", "counts": { "antennas": 28, "splitters": 6 } },
  "verification": { "status": "failed",    "error": "Simulated provider timeout" }
}
```

Counts must be nonnegative integers for every equipment type. Fixtures are validated when the server starts: a malformed file stops startup with a message naming the file and the field. Unknown keys are rejected so typos do not pass silently.

| Fixture | Initial scan | Verification scan | Result |
|---|---|---|---|
| `demo` | 28 antennas, 6 splitters | 26 antennas, 6 splitters | 201, warning, $8,680 |
| `verification_failure` | 28 antennas, 6 splitters | fails | 201, failure warning, $8,680 |
| `initial_failure` | fails | not reached | 502, nothing saved |

## Architecture

Light "ports and adapters": the business rules know nothing about HTTP, SQLite or files, and the service depends on interfaces, not on fixture paths.

```
src/
  domain/      types, pricing.ts, consolidation.ts, errors.ts   pure functions, no I/O
  ports/       ScanProvider.ts, EstimateRepository.ts           interfaces the service depends on
  adapters/    MockScanProvider.ts, fixtureLoader.ts,           mock provider + fixture files,
               fixtureSchema.ts, SqliteEstimateRepository.ts    SQLite storage
  services/    EstimateService.ts                               orchestrates the three stages
  http/        app.ts, routes.ts, validation.ts, errorHandler.ts  Express layer
  config.ts, server.ts                                          configuration and wiring (composition root)
fixtures/      demo.json, verification_failure.json, initial_failure.json
tests/         unit, integration (supertest) and persistence tests
```

Design decisions and trade-offs:

- **Pure domain functions.** `calculatePrice` and `consolidate` take values and return values. They are trivial to test and to change (a new equipment type or a different rule touches only the domain).
- **Provider abstraction.** `ScanProvider` has two methods, `listFixtures()` and `scan(fixture, stage)`. `MockScanProvider` receives already-loaded fixtures and never touches the file system. A real provider would replace it only in `server.ts`.
- **One error class per failure kind, mapped in one place.** `errorHandler.ts` is the only place that turns errors into status codes. Only `ProviderError` is absorbed during the verification scan; any other error is a bug and surfaces as a 500 instead of being disguised as a failed scan.
- **SQLite, one table.** Scalars get their own columns; `stages`, `scans`, `selected`, `line_items` and `warnings` are stored as JSON text because they are always read and written together with the estimate. Normalizing them would add joins for no benefit here. Queries are parameterized.
- **Async interfaces everywhere**, even though SQLite is synchronous, so a networked database or a real provider would not change the service.
- **Fixtures live in a `Map`**, so ids like `constructor` or `__proto__` can never match an inherited property.
- **Validation at the edge.** zod runs before the service, so invalid input never reaches the provider or the database.

## Tests

`npm test` runs everything. Coverage by area:

| File | What it covers |
|---|---|
| `pricing`, `consolidation` | the price rules and the selection rule, including edge cases |
| `mockScanProvider`, `fixtureLoader` | the provider, the three shipped fixtures, malformed fixtures |
| `sqliteEstimateRepository` | round trips, `null` verification, hostile ids, reopening the same file |
| `estimateService` | all three stages, discrepancy, verification failure, initial failure (nothing saved), unknown fixture |
| `validation`, `config` | every invalid-input case and its message; environment configuration |
| `api` | HTTP acceptance cases: valid creation and retrieval, discrepancy, verification failure, initial failure (502), invalid input (400), unknown fixture, 404, 500 without leaking details |

How the key requirements are checked:

- **Nothing persisted on failure.** The failure tests open the SQLite file with a separate connection and count rows, so they check what is really on disk.
- **Survives a restart.** `api.test.ts` creates an estimate, closes the database, builds a brand-new repository, service and app over the same file, and reads the estimate back. This simulates a restart inside one test process; it was also checked manually with two real server processes (see "Check persistence across a restart" above).
- **Provider failures are distinguishable from client errors.** 502 `provider_failure` versus 400 `validation_error` / `unknown_fixture`, asserted together in one test.

## Scope notes

Not implemented, as allowed by the statement: frontend, PDF parsing, real AI calls, hosting, authentication, background jobs, exports.

Known limits, on purpose: one SQLite file means a single server process; there is no endpoint to list estimates; logging is plain `console`. Nothing from the required list is left incomplete.
